# Migrating from Browser Testbench 0.4.x

## Breaking changes

There are no intentional source-level breaking changes in 0.5.0. Existing constructors, `open()`, `videoPath`, positional wait timeouts, `screenshotBase64()`, and `screenshot(path, fullPage)` remain supported.

An existing 0.4.x client can upgrade without changing its calls. Review the behavior changes below when a project depends on Android loopback URL rewriting, parses error messages, sends large JSON payloads, or expects a failed cleanup to release a target immediately.

## Preferred 0.5.0 APIs

| 0.4.x call                                       | Preferred 0.5.0 call                                                      |
| ------------------------------------------------ | ------------------------------------------------------------------------- |
| `open({ target, videoPath })`                    | `open({ target })`, then `session.recording.start({ outputPath, scope })` |
| `waitForElement(selector, 90_000)`               | `waitForElement(selector, { timeoutMs: 90_000, signal })`                 |
| large Base64 arguments in `evaluate()`           | `testbench.assets.upload(pathOrBuffer)`                                   |
| raw `appium:avdArgs` camera arguments            | `media: { camera: { facing: "back", source: asset } }`                    |
| `appium:autoGrantPermissions` plus project ADB   | declarative `permissions` on `open()`                                     |
| emulator URL rewritten to `10.0.2.2`             | `localOrigins: "reverse"` with unchanged loopback URL                     |
| `screenshotBase64()` for geometry-sensitive work | `captureScreenshot({ scope })`                                            |

`videoPath` is internally implemented through the same stop-before-browser lifecycle. `appium:autoGrantPermissions: true` remains accepted for Android browser sessions and maps camera and microphone to the new native/origin permission implementation when an initial URL is present.

## Observable behavior changes

- Android emulator loopback URLs remain on `127.0.0.1` or `localhost` by default.
  Set `localOrigins: "emulator-host"` explicitly only when the application requires the old `10.0.2.2` behavior. The resulting origin may not be a secure context.
- Errors returned by the 0.5.0 server are `TestbenchError` instances with stable `code`, `operation`, and `details` fields. Code that asserts complete error-message strings should assert `code` instead.
- JSON requests over 1 MiB now fail with `PAYLOAD_TOO_LARGE`. Upload binary data through `testbench.assets.upload()`.
- Selector actions retry exactly once only after a stale-element driver error. Other click failures, including covered or disabled elements, are still returned immediately.
- A failed cleanup keeps a serial target quarantined instead of making a still-used device available to another session.
- Sessions have a 90-second lease. The 0.5.0 client maintains it automatically; custom REST clients must renew it with `POST /v1/sessions/:id/lease` before it expires.
- Mobile recording stops before browser teardown, so the final frame no longer contains the launcher or home screen.
- Mobile recording requires `ffprobe` on the Testbench host to validate the native MP4 output and FFmpeg to crop viewport recordings and stabilize irregular frame timing or duration. Capability discovery reports their absence before a session starts. Structured mobile screenshots do not require external media tools.

## Upgrade checklist

1. Upgrade the client and Testbench server together; their versions must match.
2. Keep existing 0.4.x calls or adopt the preferred APIs from the table incrementally.
3. Replace assertions on complete error text with assertions on `TestbenchError.code`.
4. Check Android tests that expect `10.0.2.2`; choose `localOrigins: "reverse"` or the explicit `"emulator-host"` fallback.
5. Move binary `evaluate()` payloads larger than 1 MiB to the asset API.
6. Install `ffmpeg` and `ffprobe` when using mobile recording.
