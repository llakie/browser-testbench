# Browser Testbench 0.5.0

[English](./0.5.0.md)

Version 0.5.0 ergänzt reproduzierbare Geräteaufnahmen, Session-Assets, sichere Android-Loopback-Origins, deklarative Browserberechtigungen und statische Kamerabilder.

## Voraussetzungen

- Node.js 22.12 oder Node.js 24 und neuer
- FFmpeg und ffprobe auf dem `PATH` für Aufnahmen, Viewport-Beschnitt und mobile Viewport-Screenshots
- Android SDK Platform Tools für Android-Targets
- die in der Setup-Oberfläche aufgeführten Appium-Treiber

Die Capability-Antwort meldet vor dem Session-Start, wenn Aufnahmen oder Viewport-Captures wegen fehlender Medienwerkzeuge nicht verfügbar sind.

## Capabilities

Prüfe Anforderungen vor aufwendiger Arbeit mit `target.require()` und übergib zwingende Anforderungen zusätzlich an `open({ require })`, damit der Server sie durchsetzt:

```ts
const testbench = new RemoteTestbench();
const target = await testbench.target("chrome-android-browser-testbench-api-36");

target.require({
  localOrigins: { reverse: true },
  permissions: { native: ["camera"], origin: ["camera"] },
  mediaInjection: { cameraImage: true },
  recording: { viewport: true, geometry: true, marks: true },
});
```

Capabilities unterscheiden Server-Limits von Target-Funktionen. Die aktuellen Limits betragen 1 MiB pro JSON-Anfrage, 50 MiB pro Asset und 100 MiB Assets pro Session.

## Android-Kamerasession

Assets akzeptieren Buffer und Pfade relativ zum aufrufenden Prozess:

```ts
const card = await testbench.assets.upload("./assets/de/de/card.jpg", {
  contentType: "image/jpeg",
});

const session = await testbench.open({
  target: target.id,
  url: "http://127.0.0.1:4301",
  localOrigins: "reverse",
  permissions: [{ name: "camera", origin: "http://127.0.0.1:4301" }],
  media: { camera: { facing: "back", source: card } },
});
```

`localOrigins: "reverse"` ist bei Android-Loopback-URLs der Standard. Testbench richtet dafür ein Session-eigenes `adb reverse`-Mapping ein und belässt den Browser-Origin auf `localhost` oder `127.0.0.1`. Der unsichere Emulator-Host-Fallback ist ausschließlich über `localOrigins: "emulator-host"` verfügbar.

Der Server ermittelt das aktive Android-Browserpaket, erteilt dessen native Kamera- oder Mikrofonberechtigung, erteilt die angeforderte Browser-Origin-Berechtigung vor der Navigation und stellt beim Cleanup den vorherigen Zustand wieder her.

## Aufnahme und Zeit

```ts
await session.recording.start({ outputPath: "./export/raw.mp4", scope: "viewport" });
await session.mark("story.start");
await session.waitForElement("[data-testid=price-result]", { timeoutMs: 90_000, signal });
await session.mark("price.visible");
const recording = await session.recording.stop();
await session.close();
```

`stop()` beendet den nativen Recorder vor dem Browser-Teardown, prüft die MP4-Datei mit ffprobe, überträgt sie atomar und kontrolliert Dateigröße und SHA-256. Das Ergebnis enthält Codec, Container, Abmessungen, Dauer, Zeitbasis, durchschnittliche Bildrate, VFR-/CFR-Modus, geordnete Marker und Geometrie-Samples.

Geometrien verwenden links/oben inklusive und rechts/unten exklusive Rechtecke. `viewportInVideo` wird in Videopixeln angegeben. CSS-Viewport-Abmessungen und Safe-Area-Werte verwenden CSS-Pixel. Unterteilungen in Browser- und System-Insets bleiben `null`, wenn die Plattform sie nicht zuverlässig bestimmen kann.

## Screenshots

Nutze `captureScreenshot()` für explizite Semantik:

```ts
const image = await session.captureScreenshot({ scope: "viewport" });
```

Die je Target unterstützten Scopes werden als `screen`, `viewport`, `fullPage` und `element` gemeldet. Ergebnisse enthalten Abmessungen und Screen-/Viewport-Zuordnungen. Nicht unterstützte Anfragen schlagen mit `SCREENSHOT_SCOPE_UNSUPPORTED` fehl. Das bestehende `screenshotBase64()` bleibt kompatibel und behält sein treiberabhängiges Verhalten aus 0.4.

## Timeouts, Abbruch, Leases und Cleanup

Waits und Navigation akzeptieren `{ timeoutMs, signal }`. Der Transport-Timeout entspricht dem Operations-Timeout plus fünf Sekunden Netzwerkreserve. Abbrüche durch den Aufrufer verwenden `OPERATION_ABORTED`; abgelaufene Operations-Timeouts verwenden `WAIT_TIMEOUT`.

Sessions haben standardmäßig eine Server-Lease von 90 Sekunden und einen Client-Heartbeat von 30 Sekunden. Target-Locks speichern Besitzer, Session, PID und Prozessstart-Identität. Cleanup-Fehler halten ein serielles Target in Quarantäne, bis ein erneuter Versuch den erfolgreichen Cleanup bestätigt. `close()` und `recording.stop()` sind idempotent.

## Fehler und Diagnose

Neue und geänderte Fehler sind `TestbenchError`-Instanzen mit `code`, `message`, `operation`, optionaler `sessionId` und serialisierbaren `details`. Das Release definiert `TARGET_BUSY`, `SESSION_LEASE_EXPIRED`, `STALE_ELEMENT`, `PAYLOAD_TOO_LARGE`, `ASSET_LIMIT_EXCEEDED`, `WAIT_TIMEOUT`, `OPERATION_ABORTED`, `LOCAL_ORIGIN_UNAVAILABLE`, Fehler für Berechtigungen, Medien und Aufnahmen sowie `SCREENSHOT_SCOPE_UNSUPPORTED` und `CAPABILITY_UNAVAILABLE`.

`session.diagnosticBundle()` liefert bereinigte Session-Metadaten, Operationen, Marker, DOM, Viewport-Screenshot, Browserereignisse, Berechtigungen, Aufnahmestatus und Cleanup-Status. Authorization- und Cookie-Header werden nie im Klartext ausgegeben.
